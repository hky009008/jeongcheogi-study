S02 · 상태 패턴 vs 전략 패턴 — 누가 갈아 끼우나

2026-10-26 · A3 보충 자료 · 디자인패턴

보충A3 상태 패턴과 전략 패턴을 두 번 틀렸어요(D014-2는 처음에 전략·템플릿 메서드, D022-5는 전략). 그리고 D022 5번을 풀면서 “동전을 넣는 건 바깥(클라이언트)인데, 그럼 전략 아닌가?”라는 질문이 나왔어요. 이 페이지는 그 질문 하나에 끝까지 답해요.

  • 상태 vs 전략을 “구현 객체를 누가 고르나”로 가를 수 있다
  • “바깥에서 무언가 들어온다”가 곧 전략이라는 뜻이 아님을 코드로 설명할 수 있다
  • 문제 문장 속 단서로 상태·전략·템플릿 메서드를 구별할 수 있다
이 페이지의 흐름① 헷갈린 지점 정확히 짚기 → ② 두 패턴의 구조가 왜 쌍둥이인지 → ③ 같은 크기의 코드로 나란히 비교 → ④ 자판기를 한 단계씩 추적 → ⑤ 문제 단서 표와 연습 문제.

1. 헷갈린 지점 — “바깥에서 뭔가 들어오면 전략?”

핵심 한 줄 두 패턴 다 바깥에서 무언가 들어와요. 들어오는 게 구현 객체면 전략, 사건(요청)이면 상태예요.

질문의 출발점은 자연스러워요. 전략 패턴을 배울 때 “클라이언트가 바깥에서 골라 넣는다”고 했는데, 자판기도 동전을 바깥에서 사람이 넣으니까요.

그런데 소프트웨어에서 바깥이 아무것도 안 하는 객체는 없어요. 모든 객체는 누군가 메서드를 불러 줘야 움직여요. 그러니 “바깥에서 뭔가 했다”는 두 패턴을 가르는 기준이 될 수 없어요.

진짜 기준은 바깥이 무엇을 넘겨주느냐예요. 전략에서는 클라이언트가 new CardPay()처럼 구현 객체 자체를 골라서 넘겨요. 상태에서는 사람이 동전을 넣었다는 사건만 알려 주고, 그다음에 어떤 상태 객체로 바꿀지는 자판기가 정해요. 동전 넣는 사람은 “HasCoin 상태로 바꿔 줘”라고 말하지 않았어요.

2. 왜 이렇게 헷갈리나 — 구조가 쌍둥이

핵심 한 줄 클래스 그림은 똑같아요. 그래서 그림이 아니라 문장의 주어로 가려야 해요.

두 패턴 모두 인터페이스 하나, 그걸 구현한 클래스 여럿, 그리고 그중 하나를 들고 있다가 일을 맡기는(위임) 원래 객체로 이뤄져요. GoF 책에서도 두 패턴의 클래스 다이어그램은 거의 같은 모양이에요.

그래서 시험 문제는 구조를 길게 설명한 다음, 마지막에 “누가 바꾸는지”를 한 구절로 슬쩍 넣어요. 이 한 구절을 놓치면 둘 중 아무거나 그럴듯해 보여요. 출제자 입장에선 아주 효율적인 함정이에요.

3. 코드로 나란히 — 클라이언트 코드에 무엇이 보이나

핵심 한 줄 클라이언트 코드에 구체 클래스 이름이 보이면 전략, 사건 메서드만 보이면 상태.

먼저 전략이에요. 결제 방식을 고르는 건 사용자의 선택이고, 그 선택을 클라이언트 코드가 setStrategy(new CardPay())로 직접 넣어 줘요. Payment는 무엇이 들어왔는지 몰라도 그냥 위임해요. 카드와 포인트는 서로를 몰라요. 서로 바꿔 탈 일이 없으니까요.

// ── 전략: 클라이언트가 고른다 ──
interface PayStrategy { void pay(int amount); }
class CardPay  implements PayStrategy { public void pay(int a) { /* 카드 승인 */ } }
class PointPay implements PayStrategy { public void pay(int a) { /* 포인트 차감 */ } }

class Payment {
    private PayStrategy strategy;
    void setStrategy(PayStrategy s) { this.strategy = s; }   // 바깥이 넣어 줌
    void pay(int amount) { strategy.pay(amount); }           // 위임
}

// 클라이언트
Payment p = new Payment();
p.setStrategy(new CardPay());   // ← 클라이언트가 CardPay를 '알고' 골랐다
p.pay(10000);

다음은 상태예요. 클라이언트는 insertCoin(), pressButton()만 불러요. HasCoin이라는 클래스 이름은 클라이언트 어디에도 없어요. 상태를 바꾸는 setState(new HasCoin())는 NoCoin 상태 객체 안에 있어요. 그래서 상태 객체들은 서로를 알아요. “나 다음엔 누구”가 각자 안에 적혀 있거든요.

// ── 상태: 객체가 스스로 바꾼다 ──
interface State { void insertCoin(Machine m); void pressButton(Machine m); }

class NoCoin implements State {
    public void insertCoin(Machine m)  { m.setState(new HasCoin()); }  // ← 스스로 전환
    public void pressButton(Machine m) { System.out.println("동전을 넣어 주세요"); }
}
class HasCoin implements State {
    public void insertCoin(Machine m)  { System.out.println("이미 동전이 있어요"); }
    public void pressButton(Machine m) {
        m.dispense();
        m.setState(m.stock() == 0 ? new SoldOut() : new NoCoin());     // ← 스스로 전환
    }
}

class Machine {
    private State state = new NoCoin();
    void setState(State s) { this.state = s; }        // 상태 객체들이 부름
    void insertCoin()  { state.insertCoin(this); }     // 위임
    void pressButton() { state.pressButton(this); }    // 위임
}

// 클라이언트
Machine vm = new Machine();
vm.pressButton();   // "동전을 넣어 주세요"
vm.insertCoin();    // ← 사건만 보냄. HasCoin이라는 이름은 모른다
vm.pressButton();   // 음료가 나옴 — 같은 버튼인데 동작이 달라졌다
보는 곳전략상태
클라이언트가 넘기는 것구현 객체(new CardPay())사건(insertCoin())
교체 코드가 있는 곳클라이언트상태 객체 안(또는 Context 안)
구현 객체끼리서로 모름(독립)서로 앎(다음 상태 지정)
교체 시점바깥이 원할 때내부 상태가 바뀔 때 자동
목적알고리즘을 갈아 끼우기상태에 따라 행동이 달라지기

4. 자판기를 한 단계씩 추적하기

핵심 한 줄 사용자는 같은 버튼을 눌렀는데 결과가 달라요. 그 사이에 상태를 바꾼 건 사용자가 아니라 자판기예요.

위 상태 코드를 실제로 돌린다고 생각하고, 한 줄씩 따라가 볼게요. 표의 “누가 상태를 바꿨나” 열을 보면 사용자가 상태를 고른 적이 한 번도 없어요.

↔ 표가 넓어요. 옆으로 밀어서 보세요

사용자가 한 일그때 상태결과다음 상태누가 상태를 바꿨나
버튼 누름동전 없음“동전을 넣어 주세요”동전 없음—
동전 넣음동전 없음동전 받음동전 있음NoCoin 객체
버튼 누름동전 있음음료 나옴동전 없음HasCoin 객체
동전 넣음 → 버튼(마지막 1개)동전 있음음료 나옴품절HasCoin 객체

같은 “버튼 누름”이 첫 줄과 셋째 줄에서 다르게 동작했어요. 그 차이를 만든 건 사용자의 선택이 아니라 자판기의 현재 상태예요. 이게 상태 패턴의 정의 그대로예요. “객체의 내부 상태가 바뀌면 행동이 바뀌는 것처럼 보이게 한다.”

반대로 같은 자판기를 전략으로 만들면 어떻게 될까요? 사용자가 “지금부터 카드 결제 모드로” 버튼을 눌러 결제 방식을 직접 고르는 기능이 그 예예요. 이건 사용자가 구현을 골랐으니 전략이에요. 같은 기계 안에 두 패턴이 같이 있을 수도 있어요.

5. 템플릿 메서드까지 — 셋을 한 번에 가르기

핵심 한 줄 상속으로 일부 단계만 채우면 템플릿 메서드, 실행 중에 객체를 갈아 끼우면 상태나 전략.

D014-2 처음 답이 템플릿 메서드였으니 같이 정리해요. 템플릿 메서드는 상위 클래스가 처리 순서(골격)를 고정하고, 하위 클래스가 빈칸 단계만 채우는 상속 구조예요. 실행 중에 객체를 바꿔 끼우는 일이 없어요. 어떤 하위 클래스로 만들었는지가 처음부터 정해져 있어요.

문제 속 단서정답
사용자·클라이언트가 선택해 넣음, 알고리즘 교체, 결제·정렬·할인 방식전략
상태마다 클래스, 스스로·저절로 전환, 같은 요청에 다른 동작상태
상위 클래스가 순서 고정, 하위 클래스가 일부 단계 구현, 상속템플릿 메서드
상태가 바뀌면 여러 구독자에게 자동 통보옵서버
골라 주면 전략, 스스로 바뀌면 상태, 상속으로 빈칸 채우면 템플릿. 문제에서 “누가”를 찾고, 그게 바깥이 고르는 거면 전략이에요. 바깥이 사건만 보냈으면 상태예요.
“사용자가 동전을 넣는다”, “사용자가 주문을 취소한다”처럼 사용자가 등장한다고 전략이 아니에요. 사용자가 구현 방식을 고르는지, 아니면 사건만 일으키는지 보세요.

연습 문제 (채점 완료 · 6/6)

6문제 모두 “누가 고르나”를 다른 상황으로 물어요. 선지를 보기 전에 문제에서 “누가”에 먼저 동그라미를 쳐 보세요.

  1. 지도 앱에서 사용자가 ‘최단 거리·최소 시간·무료 도로’ 중 하나를 고르면, 앱은 그에 맞는 경로 계산 객체를 내비게이터에 넣어 주고 내비게이터는 그 객체에 경로 계산을 맡긴다. 이 설계에 해당하는 패턴은?
    정답·해설② 전략. 사용자가 고른 계산 객체를 넣어 줘요.
  2. 문서 객체가 ‘초안·검토 중·게시됨’ 상태를 각각 클래스로 두고 ‘게시’ 요청을 현재 상태 객체에 맡긴다. 검토가 승인되면 문서 객체가 스스로 현재 상태 객체를 ‘게시됨’으로 바꾸어, 같은 ‘게시’ 요청이라도 동작이 달라진다. 이 설계에 해당하는 패턴은?
    정답·해설③ 상태. 문서 객체가 스스로 ‘게시됨’으로 바꿔요.
  3. 상위 클래스 ‘음료 만들기’가 ‘물 끓이기 → 우리기 → 컵에 따르기 → 첨가물 넣기’ 순서를 고정하고, 하위 클래스 ‘커피’와 ‘차’가 ‘우리기’와 ‘첨가물 넣기’ 단계만 각각 구현한다. 이 설계에 해당하는 패턴은?
    정답·해설④ 템플릿 메서드. 상위가 순서를 고정하고 하위가 빈칸만 채우는 상속 구조예요.
  4. 상태 패턴과 전략 패턴을 구별하는 설명으로 가장 알맞은 것은?
    정답·해설② 전략은 클라이언트가 고르고, 상태는 객체가 스스로 바꿔요. ③은 반대로 쓴 함정이에요(상태 객체들이 서로 알아요).
  5. 쇼핑몰 주문 객체가 ‘결제 대기·결제 완료·배송 중’을 각각 클래스로 두었다. 고객이 ‘취소’ 버튼을 누르면 주문 객체는 그 요청을 현재 상태 객체에 맡기고, 결제가 끝나면 주문 객체가 스스로 ‘결제 완료’ 객체로 바꾼다. 고객이 버튼을 누른다는 점을 고려할 때 이 설계는?
    정답·해설② 상태. 고객은 사건(버튼)만 보내고, 상태 전환은 주문 객체가 해요. 사용자가 등장한다고 전략이 아니에요.
  6. 정렬 유틸리티가 비교 규칙을 담은 객체(Comparator)를 호출하는 쪽에서 받아, 정렬 중 두 원소를 비교할 때마다 그 객체에 판단을 맡긴다. 이 설계에 해당하는 패턴은?
    정답·해설① 전략. 호출하는 쪽이 비교 규칙 객체를 골라 넣어요(Comparator).

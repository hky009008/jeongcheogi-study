D023 · 4주차 주간 종합 복습 — 인터페이스부터 형상관리까지

2026-10-25 · A4·A5·A6 주간 종합 복습

복습A4A5A6 이번 주(D017~D021)는 범위가 넓었어요. 시스템끼리 잇는 기술(A4), 어떤 방식으로 얼마에 만들지(A5), 만든 코드를 검사하고 지키는 법(A6)까지요. 오늘은 이걸 요약표로 압축하지 않고, D015에서 시작한 쇼핑몰 프로젝트를 이어서 따라가며 한 줄기로 다시 꿰어요.

  • A4 연계 기술·통신 유형·EAI·미들웨어를 쇼핑몰 연결 하나하나에 맞춰 고를 수 있다
  • A5 생명주기·방법론·비용 산정·테일러링·CMMI가 각각 어떤 질문에 답하는지 설명할 수 있다
  • A6 드라이버·스텁, 형상관리 4활동, 버전관리 3방식을 구별할 수 있다
오늘 이야기의 흐름① 개념 지도 → ② 장면 1~2: 외부 시스템과 잇기(A4) → ③ 장면 3~5: 방식·비용·우리 조직에 맞추기(A5) → ④ 장면 6~7: 만들고 지키기(A6) → ⑤ 한 장으로 꿰기 → ⑥ A1~A3 누적, 헷갈린 짝만.

1. 개념 지도

핵심 한 줄 이번 주 = 잇고(A4) → 방법·비용을 정하고(A5) → 만들고 지킨다(A6).

D015에서 진수 님은 쇼핑몰 주문 시스템의 인터페이스 담당이 되어, 외부 시스템 4개(PG사·국세청·물류사·사내 회계)와의 연결 목록을 만들었어요. 이번 주는 그다음 이야기예요. 연결을 실제로 무엇으로 이을지 정하고, 팀이 어떤 방식으로 얼마 들여 만들지 정하고, 코드를 짜기 시작하면서 검사하고 관리하는 데까지 가요.

2. 장면 1 — 무엇으로 잇나 (연계 기술·통신 유형)

핵심 한 줄 연계 기술은 선의 종류, 통신 유형은 보내고 기다리는 법.

D015의 인터페이스 목록에는 “누가 보내고 누가 받나”까지 적혀 있었어요. 이제 그 선을 실제로 무엇으로 이을지 골라야 해요. 상대가 DB를 열어 주면 DB로 붙고, 함수를 공개하면 API로 부르고, 포트만 열어 두면 소켓으로 붙어요.

연계 기술어떻게 잇나쇼핑몰 예
DB LinkDB에 링크 객체를 만들어 상대 DB를 직접 조회사내 회계 DB에서 매출 조회
DB Connection커넥션 풀로 DB에 접속주문 서비스 → 주문 DB
API / Open API상대가 공개한 함수로 접근PG사 결제 승인 API
JDBC자바 프로그램이 DB에 붙는 드라이버스프링 앱의 DB 연결
Hyperlink웹 링크로 이동배송 조회 페이지로 링크
Socket서버가 포트를 열면 클라이언트가 연결물류사 실시간 출고 연동

선을 골랐으면 “보낸 다음 어떻게 기다리나”를 정해요. 이게 통신 유형이에요. 보내고 끝이면 단방향, 응답이 올 때까지 기다리면 동기, 요청해 두고 딴 일을 하다가 응답을 따로 받으면 비동기예요. 결제 승인은 결과를 받아야 주문을 완료하니 동기, 출고 요청은 물류사가 나중에 완료 신호를 보내니 비동기예요.

통신 유형과 자주 섞이는 게 처리 유형이에요. 처리 유형은 기다리는 법이 아니라 모으는 법이에요. 한 건씩 바로(실시간), 조금 모았다가(지연), 정해진 시각에 한꺼번에(배치). 세금계산서를 매일 23시에 몰아 보내는 건 처리 유형으로 배치예요. 출제자는 “통신 유형이 아닌 것”에 배치를 끼워 넣어요.

누가 보내고 받는지, 가운데 누가 거치는지는 D015에서 정했어요. 아래는 그 구조를 다시 본 그림이에요.

→ 이 장면의 결과물: 연결마다 선의 종류와 통신 방식이 정해졌어요. 그런데 연결이 4개를 넘어가면 선이 엉키기 시작해요. 그걸 묶는 방법이 다음 장면이에요.

3. 장면 2 — 연결이 많아지면 어떻게 묶나 (EAI·미들웨어)

핵심 한 줄 EAI는 묶는 모양(4가지), 미들웨어는 가운데서 무엇을 들고 다니나(6가지).

쇼핑몰이 커져 연결할 시스템이 열 개, 스무 개가 되면 하나하나 직접 잇는 게 감당이 안 돼요. 그래서 기업 안 애플리케이션들을 한 구조로 묶는 EAI(Enterprise Application Integration)를 써요. 묶는 모양이 네 가지예요.

EAI 모양구조얻는 것 / 내주는 것
Point-to-Point1:1로 직접 연결(그물)단순 / 시스템이 늘면 선이 폭증, 변경·재사용 어려움
Hub & Spoke가운데 허브 하나를 거침(별)확장·유지보수 쉬움 / 허브 장애 시 전체 멈춤
Message Bus애플리케이션 사이에 미들웨어 버스확장성·대용량 처리 유리
Hybrid그룹 안은 허브, 그룹 사이는 버스둘의 장점을 섞음

Hub & Spoke는 환승 허브 공항과 같아요. 어디든 한 번만 갈아타면 가지만, 허브 공항에 폭설이 오면 전국 항공편이 같이 묶여요.

묶는 모양을 정했으면, 그 가운데서 실제로 통신을 대신해 주는 소프트웨어가 필요해요. 그게 미들웨어예요. 여섯 가지는 “가운데서 무엇을 들고 다니나”로 가르면 빨라요.

미들웨어들고 다니는 것시험 키워드
DB 미들웨어DB 접속ODBC, IDAPI
RPC원격 함수 호출원격 프로시저를 로컬처럼
MOM메시지(편지)큐, 비동기, 느려도 안정
TP-Monitor거래(트랜잭션)항공 예약·은행, 빠른 응답
ORB객체 요청CORBA
WAS동적 웹 요청Tomcat, JEUS, WebLogic
MOM과 TP-Monitor는 둘 다 “서버 사이 중계”처럼 들려요. 메시지·비동기면 MOM, 트랜잭션·즉시 응답이면 TP-Monitor예요.

→ 이 장면의 결과물: 연결 설계가 끝났어요. 이제 팀이 이걸 어떤 방식으로, 얼마 들여 만들지 정할 차례예요. A5로 넘어가요.

4. 장면 3 — 어떤 순서·관점으로 만드나 (생명주기·방법론)

핵심 한 줄 생명주기 모델은 순서, 개발 방법론은 관점. 둘은 서로 다른 질문의 답이에요.

A5 용어가 많아 보이는 건 서로 다른 질문의 답이 섞여 있어서예요. “분석·설계·구현·테스트를 어떤 순서로 돌까?”의 답이 생명주기 모델이고, “시스템을 무엇을 중심으로 쪼갤까?”의 답이 개발 방법론이에요.

생명주기 모델은 앞 모델의 약점을 고치며 이어졌어요. 폭포수는 단계를 순서대로 밟고 문서로 승인받아 넘어가요. 요구를 늦게 확인하는 게 약점이라, 견본부터 보여 주고 피드백을 받는 프로토타입 모델이 나왔어요.

큰 프로젝트의 위험을 다루려고 나선형 모델(보헴)이 나왔어요. 계획 수립 → 위험 분석 → 개발 → 고객 평가를 한 바퀴로 돌며, 바퀴마다 위험 분석이 있어 대규모·고위험 프로젝트에 맞아요. 이후 작게 나눠 여러 번 내놓는 반복·점진 모델과 애자일로 이어졌어요.

개발 방법론은 무엇을 중심에 두느냐로 구별해요.

방법론중심
구조적기능(처리 흐름)을 DFD로 분할
정보공학기업 전체의 데이터, 계획부터 구축까지
객체지향데이터와 행위를 묶은 객체
CBD재사용 가능한 컴포넌트 조립
제품 계열비슷한 제품군의 공통 부분 재사용

쇼핑몰은 요구가 자주 바뀌고 빨리 내놓아야 하니 반복형·애자일에, 객체지향 방법론을 고르는 게 자연스러워요.

→ 이 장면의 결과물: 일하는 순서와 관점이 정해졌어요. 다음은 “그래서 얼마 드는데?”예요.

5. 장면 4 — 얼마 드나 (비용 산정)

핵심 한 줄 COCOMO = 코드 줄 수, Putnam = 시간에 따른 인력, FP = 기능 수. COCOMO 유형(조직·반분리·내장)과 종류(기본·중간·발전)는 다른 축.

비용 산정은 크게 두 갈래예요. 경험 많은 사람이 전체를 먼저 정하는 하향식(전문가 감정, 델파이)과, 작업을 잘게 세어 합치는 상향식(LOC, 단계별 인원수)이에요. 그 위에 수학적 모형 셋이 있어요.

모형무엇을 세나짝 키워드
COCOMO예상 코드 줄 수(LOC)보헴, 조직형·반분리형·내장형
Putnam시간에 따른 인력 분포Rayleigh-Norden 곡선, SLIM
FP기능의 수와 복잡도알브레히트, ESTIMACS

COCOMO는 프로젝트 성격에 따라 유형을 셋으로 나눠요. 사내 업무용처럼 작고 익숙한 조직형(5만 라인 이하), 컴파일러·OS 같은 중간 규모 반분리형(30만 라인 이하), 실시간·하드웨어 제어처럼 크고 빡빡한 내장형(30만 초과)이에요. 쇼핑몰 주문 시스템은 조직형에 가까워요.

“기본·중간·발전”은 유형이 아니라 계산을 얼마나 자세히 하느냐의 종류예요. 선지에 “중간형”이 유형인 척 섞이면 걸러요. 그리고 PERT·CPM·간트 차트는 일정 관리 도구라 비용 산정 모형이 아니에요.

→ 이 장면의 결과물: 인력과 기간이 나왔어요. 이제 회사 표준 방법론을 이 프로젝트 크기에 맞게 고칠 차례예요.

6. 장면 5 — 우리 조직에 맞추고 지키기 (테일러링·개발 표준·프레임워크)

핵심 한 줄 테일러링 = 방법론을 프로젝트에, 개발 표준 = 프로세스를 국제 기준에, 프레임워크 = 코드를 공통 뼈대에 맞추기.

테일러링은 표준 방법론을 그대로 쓰지 않고 프로젝트 특성에 맞게 절차·산출물을 더하고 빼는 일이에요. 기준은 둘로 갈려요. 팀 회의로 바꿀 수 있는 내부 기준(목표 환경·요구사항·프로젝트 규모·보유 기술)과, 바꿀 수 없는 외부 기준(법적 제약·표준 품질 기준)이에요. 쇼핑몰은 규모가 작으니 산출물을 합치고, 결제가 있으니 개인정보·보안 검토는 빼지 못해요.

고친 프로세스가 괜찮은지 재는 잣대가 개발 표준이에요. ISO/IEC 12207은 어떤 프로세스가 있어야 하는지의 목록(기본·지원·조직), CMMI는 조직이 그걸 얼마나 성숙하게 운영하는지의 5단계, SPICE(ISO/IEC 15504)는 프로세스 능력을 0~5의 6단계로 매겨요.

CMMI 단계는 순서가 중요해요. 1 초기(개인 역량 의존) → 2 관리(프로젝트별로 관리) → 3 정의(조직 표준이 있고 프로젝트가 그걸 테일러링해서 씀) → 4 정량적 관리(수치로 측정·통제) → 5 최적화(측정 결과로 지속 개선). 방금 장면에서 한 테일러링이 바로 3단계의 모습이에요. 2단계가 “프로젝트마다 각자 잘하는 회사”라면, 3단계는 “회사 전체가 같은 레시피북을 펴 놓고 요리하는 회사”예요.

마지막으로 코드 쪽 뼈대가 개발 프레임워크예요. 공통 기능을 미리 만들어 둔 반제품이고, 특성은 모듈화·재사용성·확장성·제어의 역흐름(IoC)이에요. 내가 부르는 게 라이브러리, 나를 부르는 게 프레임워크예요. 스프링 컨트롤러를 직접 호출한 적이 없는데 요청이 오면 실행되는 게 IoC예요.

→ 이 장면의 결과물: 방식·비용·뼈대가 다 정해졌어요. 이제 진짜 코드를 짜요. A6으로 넘어가요.

7. 장면 6 — 만들고 검사하기 (단위 모듈·드라이버·스텁)

핵심 한 줄 대상을 부르는 가짜 상위 = 드라이버, 대상에게 불리는 가짜 하위 = 스텁.

쇼핑몰의 주문 모듈을 다 만들었는데, 그걸 부를 화면 모듈도, 주문 모듈이 부를 결제 모듈도 아직 없어요. 그래도 주문 모듈만 먼저 검사하고 싶어요. 그래서 빈자리에 대역을 세워요.

테스트 드라이버는 주문 모듈을 대신 호출하고 결과를 받아 주는 가짜 상위 모듈이에요. 테스트 스텁은 주문 모듈이 결제 모듈을 부를 때 대신 불려서 “승인 완료” 같은 정해진 값을 돌려주는 가짜 하위 모듈이에요. 드라이버는 큐 사인을 주는 감독, 스텁은 대사 한 줄만 받은 단역이에요. 진짜 배우가 오면 둘 다 퇴장해요.

검사 방법은 두 갈래예요. 코드 내부 경로를 보며 검사하면 화이트박스, 입력과 출력만 보며 명세대로 도는지 보면 블랙박스예요.

→ 이 장면의 결과물: 검사한 코드가 쌓이기 시작했어요. 그런데 코드는 매일 바뀌어요. 그걸 붙잡는 게 마지막 장면이에요.

8. 장면 7 — 바뀌는 코드 붙잡기 (형상관리·버전관리)

핵심 한 줄 형상관리 4활동 = 식별 → 통제 → 감사 → 기록. 버전관리는 저장소가 한 곳이면 클라이언트/서버, 각자 로컬에도 있으면 분산.

형상관리는 소프트웨어 변경을 체계적으로 추적·통제하는 활동이에요. 소스 코드만이 아니라 문서·설계서까지, 개발 전 과정이 대상이에요. 출발점은 공식 검토로 확정한 산출물인 기준선(베이스라인)이에요.

활동하는 일쇼핑몰 예
형상 식별관리할 항목을 정하고 이름·번호 붙이기주문 API 명세서 v1.0
형상 통제변경 요청을 검토·승인해 기준선에 반영“쿠폰 필드 추가” 승인
형상 감사반영된 변경이 제대로인지 무결성 확인v1.1이 승인 내용과 맞는지 점검
형상 기록결과를 기록·보고변경 이력 보고서

형상관리를 실제로 돌리는 도구가 버전관리예요. 저장소가 어디 있느냐로 세 방식이 갈려요. 공유 폴더에 파일을 복사해 쓰면 공유 폴더 방식(RCS·SCCS), 중앙 저장소 하나에 모두가 바로 커밋하면 클라이언트/서버 방식(CVS·SVN)이에요.

분산 저장소 방식(Git)은 원격 저장소를 복제한 로컬 저장소가 각자에게 있어요. 그래서 먼저 내 로컬에 커밋하고, 나중에 원격에 push해요. 문제에 “원격 저장소”라는 말이 나와도 “로컬에 커밋 → 나중에 반영”이 보이면 분산이에요. 진수 님이 매일 쓰는 git commit → git push가 바로 그 순서예요.

“형상관리는 소스 코드만”, “유지보수 단계에서만” 같은 선지는 틀려요. 문서까지, 전 과정이에요.

10. A1~A3 누적 — 헷갈리는 짝만

핵심 한 줄 3주 전 범위는 다 다시 읽지 말고, 짝을 가르는 질문 하나씩만 꺼내요.

누적 10문항에서 틀린 건 세 개였어요. 셋 다 몰라서가 아니라 비슷한 짝에서 미끄러졌어요. 그래서 이 섹션은 짝마다 가르는 질문 하나만 남겼어요.

헷갈리는 짝가르는 질문답
집합 / 합성 / 연관마름모가 있나, 색이 차 있나?빈 ◇ = 집합(부분 독립), 채운 ◆ = 합성(같이 소멸), 마름모 없음 = 연관
아키텍처 품질 속성 3측면돌아갈 때의 품질인가, 돈·일정인가, 설계 자체인가?가용성·성능·보안 = 시스템, 시장 적시성·비용 = 비즈니스, 개념적 무결성·구축 가능성 = 아키텍처
논리적 / 기능적 응집도플래그로 골라 실행하나, 기능이 딱 하나인가?플래그 선택 = 논리적(약한 편), 단일 기능 = 기능적(가장 강함)
인터뷰 / 설문소수에게 깊게인가, 다수에게 같은 질문인가?소수·심층 = 인터뷰, 다수·동일 = 설문
정방향 / 역방향 추적요구 → 구현인가, 구현 → 요구인가?정방향 = 누락 찾기, 역방향 = 근거 없는 기능 찾기
와이어프레임 / 목업 / 스토리보드 / 프로토타입뼈대인가, 실물 같은 그림인가, 설명 문서인가, 동작하나?순서대로 와이어프레임 → 목업 → 스토리보드 → 프로토타입
SOLID의 I쓰지 않는 메서드에 의존하나?그렇다면 인터페이스를 쪼개라 = ISP

D011 · 소프트웨어 아키텍처 — 설계 원리·품질 속성·패턴 8종·4+1 뷰

2026-10-13 · A3 소프트웨어 설계 > 애플리케이션 설계

A3 어제는 “아키텍처 설계 = 상위 설계”까지 봤어요. 오늘은 그 상위 설계의 원리·품질·패턴을 봐요. 현업에서 익숙한 내용이 대부분이라, 시험이 쓰는 분류 이름과 패턴 8종 키워드만 정확히 맞추면 돼요. 패턴 8종은 거의 매회 나오는 단골이에요.

  • 소프트웨어 아키텍처의 정의와 설계 원리 4가지(모듈화·추상화·단계적 분해·정보 은닉), 추상화 3종(과정·데이터·제어)을 구별한다
  • 품질 속성을 시스템·비즈니스·아키텍처 3측면으로 나누고 대표 항목을 분류한다 (ISO 9126 품질 특성과 혼동하지 않는다)
  • 아키텍처 패턴 8종(레이어·클라이언트-서버·파이프-필터·MVC·브로커·P2P·이벤트 버스·마스터-슬레이브)을 구조 그림과 키워드로 구별하고, MVC가 GoF 디자인 패턴이 아님을 안다
  • 설계 과정(설계 목표 설정 → 시스템 타입 결정 → 아키텍처 패턴 적용 → 서브시스템 구체화 → 검토)과 시스템 타입 4종을 알아본다
  • 4+1 뷰(논리·프로세스·구현(개발)·배포(물리) + 유스케이스)를 무엇을 보는 뷰인지로 구별한다

2. 아키텍처란 — 그리고 설계 원리 4가지

소프트웨어 아키텍처 = 소프트웨어의 골격이 되는 기본 구조. 구성 요소(컴포넌트) + 구성 요소 사이의 관계 + 설계·진화를 이끄는 원칙의 집합이에요. 이해관계자끼리 소통하는 도구이고, 성능·보안 같은 비기능 요구를 반영하는 가장 이른 설계 결정이에요.

건물로 치면 골조예요. 나중에 바꾸려면 비용이 가장 많이 드는 결정이라 상위(예비) 설계에서 먼저 정해요. 이 골조를 짤 때 따르는 원리는 네 가지예요.

모듈화기능을 모듈 단위로 나눔. 너무 잘게 나누면 통합 비용↑, 너무 크게 나누면 모듈 하나의 개발 비용↑
추상화전체 흐름과 본질만 먼저 설계하고, 세부는 뒤로 미룸
단계적 분해Niklaus Wirth의 하향식 전략. 상위 기능부터 하위로 점점 쪼개고, 상세 내역은 가능한 한 뒤로 미룸
정보 은닉모듈 내부(자료·로직)를 감추고, 정해진 인터페이스로만 주고받음 → 수정이 다른 모듈로 번지지 않음
하향식 설계최상위 기능 → 하위 모듈로 분해 (= 단계적 분해). 인터페이스가 먼저 정해져 통합이 수월
상향식 설계최하위 모듈부터 만들고 위로 결합. 기존 모듈 재사용에 유리, 인터페이스는 나중에 맞춤

※ 설계 원리 목록은 자료마다 조금 달라요. 시나공·흥달 계열은 오늘 본 네 가지(흥달은 분할과 정복을 더해 다섯), 일부 강의 요약은 단순성·자기서술성·추상화·정보은닉으로 적어요. 추상화·정보 은닉은 어느 쪽에도 들어가요.

추상화 3종

종류뜻현업 감각
과정 추상화자세한 수행 과정은 정의하지 않고 전체 흐름만 파악할 수 있게 설계함수 이름만 보고 호출 — sendMail() 안은 몰라도 됨
데이터 추상화데이터의 세부 속성·용도는 정의하지 않고, 데이터 구조를 대표하는 표현으로 대체ADT·interface — Queue가 배열인지 리스트인지 모름
제어 추상화이벤트 발생의 정확한 절차·방법은 정의하지 않고 대표하는 표현으로 대체이벤트 핸들러 등록 — 언제 어떻게 호출될지는 프레임워크가 처리
과데제 — 과정(흐름)·데이터(자료 구조)·제어(이벤트). 기능 추상화라는 말이 나오면 과정 추상화와 같은 뜻으로 보세요.

3. 품질 속성 — 시스템 · 비즈니스 · 아키텍처

아키텍처가 좋은지 따지는 기준을 누가 보는 품질인가에 따라 세 측면으로 나눠요.

측면대표 항목 (공통)한 자료에만 있는 항목판단 키워드
시스템성능, 보안, 가용성, 사용성, 변경 용이성기능성, 확장성, 시험 용이성, 배치성, 안정성운영 중 시스템이 어떻게 동작하나
비즈니스시장 적시성, 비용과 혜택, 예상 시스템 수명목표 시장, 공개 일정, 기존 시스템과의 통합언제 출시·얼마·얼마나 오래
아키텍처개념적 무결성, 정확성·완결성, 구축 가능성변경성, 시험성, 적응성, 일치성, 대체성설계가 하나의 일관된 개념인가, 정말 만들 수 있나
시비아 = 시스템·비즈니스·아키텍처. 아키텍처 측면은 개정구 = 개념적 무결성·정확성(완결성)·구축 가능성.
① “시장 적시성·비용·예상 수명”을 시스템 측면 선지에 섞어 내요 — 돈·출시·수명은 비즈니스예요. ② ISO 9126 품질 특성(기능성·신뢰성·사용성·효율성·유지보수성·이식성)과는 다른 분류예요. “품질 속성 3측면”을 묻는데 9126 이름이 나오면 의심하세요(9126은 D 범위에서 따로 봐요).

5. 아키텍처 패턴 — 구조의 정석

아키텍처 패턴은 자주 만나는 구조 문제에 대한 참조용 전형적 해결 방식이에요. 아키텍처 스타일·표준 아키텍처라고도 불러요. 서브시스템들과 각자의 역할, 서로의 관계 규칙·지침까지 담고 있어요. 패턴을 쓰면 개발 시간이 줄고, 검증된 구조라 품질을 예측하기 쉽고, 이해관계자끼리 소통도 쉬워져요.

패턴 8종 — 실제 모양

패턴 8종 비교표

패턴구조 한 줄결정 키워드 · 대표 예
레이어시스템을 계층으로 나누고, 마주 보는 두 계층 사이에서만 상호작용계층 · 특정 계층만 교체 쉬움
예: OSI 7계층, 3-tier
클라이언트-서버서버 하나 + 클라이언트 여럿. 서버는 항상 요청을 기다림요청-응답 · 서버 상시 대기
예: 웹 브라우저 ↔ 웹 서버
파이프-필터데이터 처리 단계를 필터로 캡슐화하고 파이프로 연결필터 재사용·재배치 쉬움 · 필터 간 데이터 변환 오버헤드
예: UNIX 셸 |, 컴파일러 단계
MVC모델(핵심 기능·데이터) · 뷰(표시) · 컨트롤러(입력 처리, 모델에 명령) 분리한 모델에 여러 뷰 · 대화형 앱
예: 웹 프레임워크(Spring MVC)
브로커중개자(브로커)가 요청에 맞는 컴포넌트를 찾아 사용자와 연결중개 · 위치 투명성 · 분산 환경
예: CORBA, RPC 미들웨어
P2P피어 하나가 클라이언트이자 서버. 중앙 서버 없음피어 · 대등 · 분산 공유
예: BitTorrent, 블록체인 노드
이벤트 버스소스가 채널에 메시지를 발행하면 그 채널을 구독한 리스너가 처리. 구성 = 소스·리스너·채널·버스발행/구독(Pub/Sub) · 비동기 · 느슨한 결합
예: Kafka 토픽 구독, 알림 서비스
마스터-슬레이브마스터가 같은 구조의 슬레이브들에 작업을 나누고 결과를 모음분할 → 회수 · 병렬 · 장애 허용
예: DB 복제, MapReduce

※ 기타 패턴으로 블랙보드(공유 지식 저장소에 여러 컴포넌트가 해답을 써 나감, 음성 인식)와 인터프리터(특정 언어로 작성된 프로그램 해석)도 가끔 선지에 나와요. 파이프-필터의 데이터 흐름은 그림처럼 한 방향이 기본인데, “양방향도 구현 가능”이라고 쓴 요약도 있어 자료마다 달라요. 방향을 단정하는 선지보다 필터·파이프·변환 오버헤드·UNIX 셸 키워드로 고르세요.

1순위 4종 레·클·파·M(레이어·클라이언트-서버·파이프-필터·MVC)부터 확실히. “서버 하나, 클라이언트 여럿”, “모델 하나, 뷰 여럿”으로 개수를 붙여 외우면 뒤집힌 선지가 바로 보여요.
  • 브로커 vs 이벤트 버스: 둘 다 가운데 무언가가 있지만, 브로커는 요청한 쪽에 맞는 서버를 찾아 연결해 주는 요청-응답이고, 이벤트 버스는 발행만 하면 구독자들이 받는 구조(발행자는 누가 받는지 모름)예요.
  • MVC vs 레이어: MVC는 역할 3분할(입력·데이터·표시), 레이어는 위아래 계층 쌓기예요.
  • “MVC는 GoF 디자인 패턴이다” ✕ — MVC는 아키텍처 패턴이에요. GoF 23개 목록에 없어요.
  • “C/S는 클라이언트 하나에 서버 여럿” ✕ — 개수를 뒤집은 선지예요.

6. 4+1 뷰 — 아키텍처를 보는 다섯 시선

아키텍처는 한 장의 그림으로 다 표현되지 않아요. Kruchten(1995)은 네 개의 뷰로 나눠 그리고, 유스케이스(시나리오) 뷰를 +1로 두어 나머지 넷을 묶고 검증하게 했어요.

뷰무엇을 보나대표 UML
논리 뷰시스템이 제공하는 기능, 구성 객체와 관계클래스, 상태
프로세스 뷰실행 중 동작 — 동시성·분산·성능, 프로세스·스레드 간 통신시퀀스, 통신, 활동
구현 뷰
= 개발 뷰		개발자가 보는 모듈·패키지 구성(소스·라이브러리 구조)컴포넌트, 패키지
배포 뷰
= 물리 뷰, 배치 뷰		소프트웨어가 올라갈 물리 노드와 네트워크 배치배치
유스케이스 뷰 (+1)
= 시나리오 뷰		시나리오로 나머지 네 뷰를 묶고 검증, 다른 뷰 설계의 출발점유스케이스
+1 = 유스케이스. 나머지 넷은 “논프구배”(논리·프로세스·구현·배포). D002에서 본 UML 다이어그램이 뷰마다 어디에 쓰이는지 짝지어 보세요 — 배치 다이어그램은 배포 뷰, 컴포넌트·패키지는 구현 뷰.

※ 원 논문 이름은 Logical·Development·Process·Physical + Scenarios예요. 그래서 국내 자료마다 구현/개발, 배포/배치/물리처럼 이름이 달라요. 각 뷰를 누가 주로 보는지(사용자·설계자·개발자 등)도 자료마다 달라서 여기엔 적지 않았어요.

7. 시험 포인트 정리

  • 아키텍처 = 구성 요소 + 관계 + 원칙 = 시스템의 골격, 상위(예비) 설계
  • 설계 원리 = 모듈화 · 추상화 · 단계적 분해 · 정보 은닉, 단계적 분해 = Wirth의 하향식
  • 추상화 3종 = 과정 · 데이터 · 제어
  • “시장 적시성 · 비용 · 예상 수명” → 비즈니스 측면, “개념적 무결성 · 구축 가능성” → 아키텍처 측면, “성능 · 가용성 · 보안” → 시스템 측면
  • “발행 · 구독 · 채널” → 이벤트 버스, “중개 · 위치 투명성” → 브로커
  • “필터 · UNIX 셸 · 변환 오버헤드” → 파이프-필터, “모델 하나 · 뷰 여럿” → MVC
  • “마주 보는 계층끼리만 · OSI” → 레이어, “클라이언트이자 서버” → P2P, “작업 분할 → 결과 회수” → 마스터-슬레이브
  • 4+1 뷰의 +1 = 유스케이스 뷰, MVC ≠ GoF 디자인 패턴
  • 참고: 아키텍처 평가 방법으로 ATAM(품질 속성 간 트레이드오프 분석)·SAAM(변경 용이성 중심)이 소개돼요.

D003 · 애자일(Agile)

2026-10-05 · A1 소프트웨어 개발 > 요구사항 확인

오늘의 목표: 현업에서 스크럼·칸반을 써 봤더라도 시험 용어와 분류는 따로 잡아야 해요. 선언문 4가치의 “더 중시하는 쪽”, 스크럼 3역할·3산출물·5이벤트, XP 5가치·실천, 칸반 WIP를 짝으로 외우고, 수험서와 최신 가이드 용어가 어긋나는 지점(개발팀/개발자, 번다운 차트의 위치)도 짚고 갈게요.

  • 폭포수와 애자일의 차이, 애자일 선언 4가치에서 더 중시하는 쪽을 구별한다
  • 스크럼의 역할·산출물·이벤트를 구별한다
  • XP의 5가치와 대표 실천을 구별한다
  • 칸반(시각화·WIP 제한·Pull)을 스크럼(고정 길이 스프린트)과 구별한다
  • 애자일 계열(린·FDD·크리스탈 등)과 비애자일 모델(폭포수·V-모델·나선형)을 구별한다

1. 큰 그림 — 폭포수 vs 애자일

애자일(Agile)은 요구가 바뀐다는 것을 전제로, 짧은 반복마다 실제로 돌아가는 결과물을 만들고 고객 피드백으로 방향을 고치는 개발 방식의 총칭이에요. 특정 방법 하나가 아니라 스크럼·XP·칸반 같은 여러 방법을 묶는 우산 개념이에요.

폭포수 (전통적)요구 분석 → 설계 → 구현 → 테스트 → 유지보수를 한 방향으로 순차 진행
계획·문서 중심, 앞 단계로 되돌아가기 어려움 → 후반 변경 비용이 큼
애자일1~4주 단위 반복(이터레이션·스프린트)마다 계획→개발→시연→회고
동작하는 결과물·고객 협력 중심 → 변화 수용

2. 애자일 선언 4가치

2001년 17명의 개발자가 발표한 애자일 소프트웨어 개발 선언(Agile Manifesto)이에요. 형식은 전부 “A보다 B를 가치 있게 여긴다” — 즉 B를 더 중시해요.

덜 중시 (그래도 가치 있음)더 중시
공정(프로세스)과 도구보다개인과 상호작용
포괄적인 문서보다작동하는(동작하는) 소프트웨어
계약 협상보다고객과의 협력
계획을 따르기보다변화에 대응하기
사작고변 — 더 중시하는 쪽은 사람(개인·상호작용) · 작동하는 SW · 고객 협력 · 변화 대응. 나머지(도구·문서·계약·계획)는 “덜 중시”.
단골 함정 세 가지
  • “변화 대응보다 계획 준수”처럼 A·B를 뒤집은 선지가 거의 매번 나와요. 내용(사작고변)으로 판단하세요.
  • “왼쪽/오른쪽” 표현은 믿지 마세요. 영문 원문은 “왼쪽을 더 중시”, 공식 한국어판은 어순이 뒤집혀 “오른쪽에 더 높은 가치”라고 써요. 좌우가 아니라 내용으로 외우는 게 안전해요.
  • “덜 중시 = 필요 없음”이 아니에요. 선언문도 “덜 중시하는 항목에도 가치가 있다”고 명시해요. “문서화를 하지 않는다”는 선지는 틀려요.

※ 공식 한국어판 용어는 “공정과 도구”, “작동하는 소프트웨어”예요. 수험서는 “프로세스와 도구”, “동작하는 소프트웨어”로 많이 써요. 같은 뜻이에요.

3. 애자일 계열 지도

스크럼 (Scrum)고정 길이 스프린트, PO·SM·개발팀, 관리 프레임워크
XP (eXtreme Programming)짝 프로그래밍·TDD·CI·리팩토링 등 개발 실천 중심
칸반 (Kanban)보드 시각화, WIP 제한, Pull 방식 흐름 관리
린 (Lean)도요타 생산 방식 → 낭비 제거, 가치 흐름
FDDFeature-Driven: 기능(feature) 단위로 설계·구현
크리스탈 (Crystal)팀 규모·중요도에 따라 방법을 색깔별로 골라 씀
ASD · DSDM적응형 SW 개발(추측·협력·학습) / 동적 시스템 개발 방법
⚠ 애자일 아님폭포수(순차), V-모델(단계별 테스트 대응), 나선형(위험 분석 반복)
키워드 → 방법 짝: 스프린트·PO·SM → 스크럼 / 짝 프로그래밍·TDD → XP / WIP 제한·보드 → 칸반 / 낭비 제거 → 린 / 기능 단위 → FDD / 위험 분석 → 나선형(비애자일)
나선형 모델도 “반복”을 하지만 핵심은 매 회전의 위험 분석이고 계획·문서 비중이 커서 애자일로 분류하지 않아요. “반복한다 = 애자일”로 고르면 틀려요.

4. 스크럼 (Scrum)

스크럼은 개발 기법이 아니라 일하는 틀(프레임워크)이에요. 코딩 방법은 규정하지 않고, 역할·산출물·이벤트만 정해요. 시험에서 가장 많이 나오는 애자일 방법이라 3·3·5로 외우면 돼요.

① 역할 3가지

역할핵심 책임시험 함정
제품 책임자 (PO, Product Owner)제품 가치 극대화. 제품 백로그 항목 작성·우선순위(순서) 결정, 이해관계자 요구 대표한 사람(위원회 아님). 스프린트 취소 권한은 PO만
스크럼 마스터 (SM)스크럼이 잘 돌아가게 촉진·코칭, 장애물 제거, 이벤트 타임박스 유지. 섬기는 리더(Servant Leader)프로젝트 관리자·지시자 아님. 백로그 우선순위 결정자 아님
개발팀 (2020 가이드: 개발자)스프린트 백로그 작성, 매 스프린트 증분 완성. 자기관리·교차기능팀 내 하위 팀·직급 구분 없음, 보통 10명 이하(스크럼 팀 전체)

※ Scrum Guide 2020은 “개발팀(Development Team)” 대신 “개발자(Developers)”, “역할” 대신 “책임(accountability)”이라고 써요. 수험서·기출은 “개발팀”이 많으니 둘 다 같은 대상으로 보면 돼요.

② 산출물 3가지 (+ 각 산출물의 약속)

산출물 (누가)내용약속
제품 백로그

③ 이벤트 5가지 (타임박스는 1개월 스프린트 기준 최대치)

※ 백로그 정제(refinement)는 공식 이벤트가 아니라 수시로 하는 활동이에요.

번다운 차트 — 진척 시각화 도구

※ 수험서에선 스크럼 도구로 함께 나오지만, Scrum Guide 2020에서는 번다운·번업 차트를 공식 산출물이 아닌 “예측 실천의 예”로만 언급해요. 공식 3산출물은 위 표의 3개예요.

3·3·5 — 역할 3(PO·SM·개발팀), 산출물 3(제품 백로그·스프린트 백로그·증분), 이벤트 5(스프린트·계획·일일·리뷰·회고)
스크럼 3기둥 투검적 — 투명성 · 검사 · 적응
스크럼 5가치 — 확약 · 집중 · 개방성 · 존중 · 용기
  • “스크럼 마스터 = 프로젝트 관리자(PM)” ✕ — 지시·통제하지 않고 촉진·코칭해요.
  • “제품 백로그 우선순위는 스크럼 마스터가 정한다” ✕ — PO예요.
  • “일일 스크럼은 관리자에게 진행 상황을 보고하는 회의” ✕ — 개발자들이 스스로 계획을 조정하는 15분 이벤트예요.

5. XP (eXtreme Programming)

켄트 벡이 정리한 방법으로, 스크럼이 “어떻게 관리할까”라면 XP는 “어떻게 코딩할까”에 집중해요. 짧은 릴리스와 고객 상시 참여로 피드백을 극단적으로(eXtreme) 자주 받는 게 핵심이에요.

5가치

단순성Simplicity
피드백Feedback
용기Courage
존중Respect
의단피용존 — 의사소통 · 단순성 · 피드백 · 용기 · 존중

※ XP 초판(1999)은 존중을 뺀 4가치, 2판(2004)에서 존중이 추가됐어요. 시험은 5가치 기준이에요.

6. 칸반 (Kanban)

도요타 생산 방식의 “간판(看板)”에서 온 방법이에요. 작업을 보드에 카드로 붙여 시각화하고, 진행 중(WIP, Work In Progress) 작업 수를 제한해서, 앞 칸이 비어야 다음 작업을 당겨오는(Pull) 방식으로 흐름을 관리해요.

스크럼고정 길이 스프린트(≤1개월) 단위로 계획·약속
PO·SM·개발팀 역할 정의
스프린트 중간 범위 변경 최소화
칸반고정 주기 없음, 연속 흐름
정해진 역할 없음, WIP 제한으로 병목 관리
기존 프로세스 위에 그대로 얹어 시작
칸반 = 보WIP풀 — 보드 시각화 · WIP 제한 · Pull. “진행 중 작업 수 제한”이 보이면 칸반.

※ Kanban University 가이드는 칸반을 “방법론이 아닌, 기존 프로세스 위에 적용하는 관리 방법”으로 설명해요. 시험에서는 애자일 계열 방법으로 분류해요.

7. 시험 포인트 정리

  • 선언 4가치: 더 중시 = 사작고변(개인·상호작용 / 작동하는 SW / 고객 협력 / 변화 대응). 뒤집은 선지 주의
  • 스크럼 3·3·5. 백로그 순서 = PO, 촉진·장애 제거 = SM, 스프린트 백로그 = 개발팀(개발자)
  • 일일 스크럼 15분, 스프린트 1개월 이하. 리뷰 = 제품(무엇), 회고 = 프로세스(어떻게)
  • XP 5가치 의단피용존, 짝 프로그래밍·TDD·CI·리팩토링·주 40시간 → XP
  • WIP 제한·시각화·Pull → 칸반, 낭비 제거 → 린, 기능 단위 → FDD
  • 비애자일: 폭포수·V-모델·나선형
지난 오답 리마인드(D001-2, 10/10 재확인 예정): 이해관계자가 모여 상충 요구를 합의 = 워크숍. 정적 분석은 도출 기법이 아니에요.

확인 문제 (채점 완료 · 2/2)

  1. 애자일 선언의 가치로 옳은 것은?
    정답·해설① 포괄적인 문서보다 동작하는 소프트웨어. 애자일 선언 4가치는 “오른쪽보다 왼쪽”(개인·상호작용 / 동작하는 SW / 고객 협력 / 변화 대응)을 더 중시해요. ②③④는 앞뒤를 뒤집은 함정이에요.
  2. 스크럼에서 제품 백로그 항목을 작성하고 우선순위(순서)를 결정할 책임이 있는 사람은?
    정답·해설② 제품 책임자(PO). 제품 백로그 작성과 순서(우선순위) 결정은 PO 책임이에요. 스크럼 마스터는 촉진·코칭·장애 제거, 개발자는 스프린트 백로그를 만들고, 이해관계자는 PO에게 요청만 해요.

D005 · 분석자동화 도구 — CASE와 SADT·SREM·PSL/PSA·TAGS

2026-10-07 · A1 소프트웨어 개발 > 분석모델 확인

오늘의 목표: 어제 그린 DFD·자료 사전 같은 분석 모델을 도구로 그리고 검사하는 분석자동화 도구, 곧 CASE예요. 지금 쓰는 모델링 툴·IDE 코드 생성기·테스트 자동화 도구의 조상이라 개념 자체는 금방 와닿을 거예요. 시험은 거의 두 가지만 물어요 — 상위/하위/통합 CASE를 어느 단계에 쓰나, 그리고 옛 대표 도구 이름과 특징의 짝.

  • 분석자동화 도구(CASE)의 정의와 역할(산출물 작성 지원 · 모델 간 오류·불일치 자동 검사)을 구별한다
  • 상위 CASE(요구분석·설계) · 하위 CASE(구현·테스트) · 통합 CASE(공통 저장소로 전 과정)를 적용 단계로 구별한다
  • CASE의 주요 기능·원천 기술과 기대효과·한계를 구별한다(“요구사항 정의가 필요 없어진다”는 오답)
  • SADT · SREM · PSL/PSA · TAGS의 이름–개발처–특징 짝을 구별한다

1. 큰 그림 — CASE란

CASE(Computer-Aided Software Engineering)는 기계 설계를 컴퓨터로 돕는 CAD에서 따온 말로, 소프트웨어 개발 과정의 산출물을 컴퓨터 도구로 작성·관리하고, 모델 사이의 오류·불일치를 자동으로 검사하는 도구를 통틀어 부르는 이름이에요. 출제기준에서는 “분석모델 확인” 아래 분석자동화 도구라는 이름으로 나와요.

출발점은 “자료 사전(메타데이터) + 그래픽 다이어그램”의 결합이에요. 손으로 그린 DFD는 자료 이름이 자료 사전과 어긋나도 아무도 모르지만, 도구 안에서 그리면 같은 저장소를 보고 있으니 어긋남을 자동으로 잡아낼 수 있죠. 어떤 단계를 돕느냐에 따라 상위·하위·통합으로 나눠요.

2. 상위 vs 하위 vs 통합 CASE

구분적용 단계하는 일 (지금으로 치면)
상위 CASE
Upper		계획 · 요구분석 · 설계
(생명주기 앞부분)		DFD·ERD 등 다이어그램 작성, 자료 사전 관리, 모델 간 모순·일관성 검사, 명세 오류 검증
예: UML·ERD 모델링 툴
하위 CASE
Lower		구현 · 테스트 · 유지보수
(생명주기 뒷부분)		코드 자동 생성, 디버깅, 테스트, 문서화, 역공학
예: 코드 생성기, 테스트 자동화 도구
통합 CASE
Integrated		생명주기 전체상위+하위 도구를 공통 저장소(Repository)로 묶어 한 산출물의 변경이 연결된 산출물로 이어지게
예: 모델·코드·테스트를 한데 묶은 개발 플랫폼

※ 형상관리·프로젝트 관리 도구는 특정 단계가 아니라 생명주기 전체에 걸치는 지원 도구로 따로 봐요. “중간(Middle) CASE” 같은 구분은 이번에 확인한 자료에 없어서 다루지 않아요.

위는 그림, 아래는 코드 — 상위 = 분석·설계 그림 그리고 검사, 하위 = 구현·테스트 코드 만들고 돌리기, 통합 = 저장소 하나로 전부.
  • “상위 CASE가 코드를 생성·테스트한다”, “하위 CASE가 요구분석 모델의 일관성을 검사한다”처럼 단계를 뒤바꾼 선지가 단골이에요.
  • “모순 검사 · 오류 검증 · 자료 흐름도 작성”이 보이면 상위, “코드 · 테스트 · 문서화”가 보이면 하위, “전 과정 · 공통 저장소”가 보이면 통합이에요.

3. CASE의 구조와 기능

CASE 도구들이 서로 맞물리는 핵심은 가운데의 저장소(Repository)예요. 모델·자료 사전·명세·코드 정보가 한곳에 모이니, 다이어그램에서 자료 이름을 바꾸면 자료 사전·문서·생성 코드가 같이 따라가요. 개발자 눈으로 보면 “하나의 스키마(메타모델)를 여러 도구가 공유하는 구조”예요.

주요 기능

그래픽 모델링DFD·ERD·구조도 등 다이어그램 작성 지원
저장소·자료 사전 관리모든 산출물 정보를 한곳에 보관
일관성·완전성 검증모델 간 모순·누락 자동 검출
문서 자동 생성명세서·보고서 출력
코드 생성설계 정보에서 코드 골격 생성
생명주기 연결단계별 산출물을 이어 변경 추적

CASE를 가능하게 한 원천 기술

구조적 기법분석·설계 방법론
+
프로토타이핑빠른 시제품
+
자동 프로그래밍코드 생성
+
정보 저장소공통 DB
+
분산처리여러 환경 연결
구프자정분 — 구조적 기법 · 프로토타이핑 · 자동 프로그래밍 · 정보 저장소 · 분산처리. 프로토타이핑은 상위 CASE의 “기능”이 아니라 CASE의 원천 기술 목록에 들어가요.

4. 기대효과 vs 한계

기대효과산출물 표준화
오류 조기 발견(모델 간 일관성 검증)
문서화 자동화
재사용성·유지보수 용이
생산성·품질 향상, 다양한 개발 모형 지원
한계도입 비용·교육(학습) 부담
도구 간 호환성 부족
특정 방법론에 종속
도구를 써도 분석·설계 판단은 여전히 사람 몫
“도구를 도입하면 요구사항 정의·분석이 필요 없어진다”는 오답이에요. CASE는 정의된 요구를 기록하고 검증하도록 도울 뿐, 무엇을 만들지 정하는 활동을 대신하지 않아요. “개발자가 필요 없어진다”, “테스트가 필요 없어진다”도 같은 계열의 함정이에요.

5. 전통적 대표 도구 4종 — 이름과 짝

CASE라는 말이 퍼지기 전후(1970~80년대)에 나온 요구분석 자동화 도구들이에요. 지금 쓸 일은 없지만 구 기출에서 “이름 ↔ 개발처 ↔ 특징” 짝으로 자주 나왔어요.

도구개발처핵심 특징
SADT
Structured Analysis and Design Technique		SofTech
(D. T. Ross)		시스템을 기능 계층으로 쪼개 박스·화살표 블록 다이어그램으로 표현하는 구조적 요구분석 기법. 뒤에 IDEF0로 표준화
SREM
Software Requirements Engineering Methodology		TRW실시간 처리 시스템 요구를 RSL(요구사항 기술 언어)로 쓰고 REVS가 자동 분석·검증해 명세서 출력
PSL/PSA
Problem Statement Language / Analyzer		미시간대
(ISDOS 프로젝트)		PSL(문제 기술 언어)로 요구를 기술하면 PSA(문제 분석기)가 분석해 보고서 출력. CASE라는 말보다 먼저 나온 CASE 도구
TAGS
Technology for Automated Generation of Systems		—시스템 공학 방법을 개발 주기 전 과정에 걸쳐 지원하는 통합 자동화 도구(요구 명세 언어 IORL 사용)

SADT 블록 다이어그램의 실제 모양

SADT의 박스 하나는 “활동(기능)” 하나예요. 화살표가 어느 변으로 들어오느냐에 따라 뜻이 정해져 있어요(입력·제어·출력·메커니즘, 머리글자 ICOM).

SADT-소프텍-블록 / SREM-TRW-RSL·REVS / PSL·PSA-미시간 / TAGS-통합
S로 시작하는 둘 중 R이 들어간 SREM이 RSL·REVS(그리고 TRW), 남은 SADT는 그림(블록). PSL/PSA는 이름 자체가 “언어 + 분석기” 한 쌍.
  • SADT와 SREM의 개발처(SofTech ↔ TRW)나 특징(블록 다이어그램 ↔ RSL/REVS)을 맞바꾼 선지가 나와요.
  • “SADT = 정형 언어로 기술” ×. 정형 언어(RSL)로 쓰는 쪽은 SREM, SADT는 도표(블록 다이어그램)예요.

※ 이 네 도구는 구 기출의 대표 예시예요. 2027 기준에서 그대로 나온다고 단정할 수는 없으니 깊게 파지 말고 짝만 외우세요. 일부 수험 자료는 SADT를 하위 CASE로 적기도 하는데, 원 자료(요구 정의·기능 분석용 모델링 기법)와 맞지 않아 여기서는 요구분석 도구로 설명했어요. 도구별 상위/하위 꼬리표는 시험 핵심이 아니에요.

6. 시험 포인트 정리

  • 분석자동화 도구 = CASE: 산출물 작성 지원 + 모델 간 오류·불일치 자동 검사
  • 상위 = 요구분석·설계(다이어그램 작성, 모순·일관성 검사) / 하위 = 구현·테스트(코드 생성, 테스트, 문서화) / 통합 = 공통 저장소로 전 과정
  • 핵심 구조 = 저장소(Repository)·자료 사전. 원천 기술 구프자정분
  • 효과: 표준화·오류 조기 발견·문서화 자동화·유지보수 용이 / 한계: 비용·호환성·방법론 종속. 요구 정의 불필요 ×
  • SADT-SofTech(소프텍)·블록 다이어그램, SREM-TRW·RSL/REVS·실시간, PSL/PSA-미시간대, TAGS-통합 자동화

7. 오답 복습 — D004-1 (어제 문제, D+1)

어제 “럼바우 OMT의 기능 모델링에 주로 쓰는 것”에서 객체 다이어그램을 골랐는데, 정답은 DFD였어요. 객체 다이어그램은 이름 그대로 객체 모델의 도구예요.

OMT 모델 (순서대로)무엇을 표현주로 쓰는 그림
① 객체 모델객체·속성·관계(정적 구조)객체 다이어그램
② 동적 모델시간·이벤트에 따른 상태 변화상태 다이어그램
③ 기능 모델입력 자료가 어떻게 처리돼 출력이 되나DFD (자료 흐름도)
객동기 — 이름이 곧 짝: 객체 → 객체도, 동적 → 상태도(움직임 = 상태 변화), 기능 → 자료 흐름(DFD). “기능 = 데이터를 처리하는 일 = DFD”로 오늘 CASE 단원의 DFD와 함께 묶어 두세요.

확인 문제 (채점 완료 · 1/3)

  1. 요구분석·설계 단계의 모델 작성과 일관성 검사를 지원하는 것은?
    정답·해설① 상위 CASE. 요구분석·설계(앞단)는 상위, 코드 생성·테스트(뒷단)는 하위 CASE예요.
  2. 분석자동화 도구의 기대효과가 아닌 것은?
    정답·해설 (오답 기록됨)③ 요구사항 정의 활동 자체가 불필요해짐. 도구는 정의한 요구사항을 기록·검증하도록 돕는 것이지 정의를 대신하지 않아요. 모델 간 일관성 검증(②)은 분석자동화 도구의 대표적인 기대효과예요. “아닌 것” 문제는 선지마다 O/X를 붙여 보세요.
  3. (오답 재확인) 럼바우 OMT의 모델과 주로 쓰는 다이어그램의 짝으로 옳은 것은?
    정답·해설 (D004-1 재확인 실패 · 다시 복습)④ 기능 모델 — DFD. 순서대로 객체 → 동적 → 기능이고 짝은 객체 다이어그램 → 상태 다이어그램 → DFD예요. 암기: “객동기 = 객상D” — 동적은 상태가 변하는 것(상태 다이어그램), 기능은 데이터가 처리되는 것(DFD).

고른 뒤 답안 복사 → 디스코드 공부 채널에 붙여넣기 하면 돼요.

D001 · 요구분석기법

2026-10-03 · A1 소프트웨어 개발 > 요구사항 확인

오늘의 목표: 요구사항 확인이 어떤 단계로 진행되는지 큰 흐름을 잡고, 상황을 보고 알맞은 기법을 고를 수 있게 만들기.

1. 요구사항이란

시스템이 제공해야 할 기능과, 그 기능이 지켜야 할 제약이에요.

기능 요구사항시스템이 무엇을 하는가
예) 회원은 비밀번호를 변경할 수 있다
비기능 요구사항그 기능을 얼마나 잘 하는가
성능·보안·가용성·사용성·호환성
예) 조회 결과를 2초 이내 표시한다
비기능 요구사항은 “빠르다” 대신 “2초 이내”, “월 가용성 99.9%”처럼 재서 확인할 수 있게 씁니다. “검증 가능한 요구사항”을 고르는 문제가 여기서 나와요.

도분명확 — 도출 · 분석 · 명세 · 확인. 이후 변경을 통제·추적하는 일은 요구사항 관리(D006)로 따로 봐요.

② 분석 — 정리하고 충돌 풀기

  • 분류: 기능/비기능, 우선순위, 변경 가능성 등으로 나눈다
  • 개념 모델링: UML·DFD 같은 모델로 표현한다
  • 할당: 요구사항을 하위 시스템에 나눠 맡긴다
  • 협상: 이해관계자 간 충돌을 풀고 우선순위를 정한다
  • 정형 분석: 수학적 기법으로 모순을 찾는다

4. 시험 포인트

  • 문제 상황을 보고 도출 기법을 고르는 유형이 많아요. 다수 → 설문, 심층 → 인터뷰, 의견 충돌 조율 → 워크숍.
  • 확인 기법에서 “작성자 제외”, “가장 공식적”이 나오면 인스펙션.
  • 정형 명세 언어 이름(Z, VDM, Petri-net)을 고르게 하는 문제도 나와요.
“빠르다”, “편리하다”처럼 잴 수 없는 표현은 검증 가능한 요구사항이 아니에요.

확인 문제 (채점 완료 · 2/3)

  1. 500명의 사용자에게 동일한 사용 패턴 질문을 단기간에 받으려면? ① 인터뷰 ② 설문 ③ 코드 리뷰 ④ 단위 테스트
    정답·해설② 설문. 많은 사용자에게 같은 문항을 빠르게 모으는 상황이에요. 인터뷰는 심층 파악용이라 500명에게는 비효율적이에요.
  2. 영업팀과 운영팀의 상충하는 요구를 함께 논의해 합의하려면? ① 워크숍 ② 정적 분석 ③ 부하 테스트 ④ 빌드 자동화
    정답·해설 (오답 기록됨)① 워크숍. 여러 이해관계자의 상충 요구를 한자리에서 조율하는 기법이에요. 나머지는 코드 분석·테스트·빌드 활동이에요.
  3. 다음 중 검증 가능한 비기능 요구사항은? ① 사용자가 주문을 취소한다 ② 화면이 빠르다 ③ 조회 결과를 2초 이내 표시한다 ④ 관리자가 재고를 수정한다
    정답·해설③. “2초 이내”는 측정할 수 있는 성능 요구사항이에요. ①④는 기능, ②는 “빠르다”가 모호해서 검증할 수 없어요.

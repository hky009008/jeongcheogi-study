D006 · 요구사항 관리 도구 — 추적표(RTM)·변경 통제·기준선

2026-10-08 · A1 소프트웨어 개발 > 분석모델 확인

오늘의 목표: Jira 이슈에 PR·테스트를 링크로 엮고, 스펙이 바뀌면 “이거 바꾸면 어디까지 영향 가?”를 따지는 그 일의 시험 버전이에요. 이름은 요구사항 관리 도구, 키워드는 딱 네 개 — 추적성(RTM) · 영향 분석 · 기준선 · CCB. 어제 배운 분석자동화 도구(CASE)와 무엇을 관리하느냐로 구별하는 게 핵심이에요.

  • 요구사항 공학의 개발(도출 → 분석 → 명세 → 확인)과 관리(변경 통제·추적)를 구별하고, 요구사항 관리 도구가 관리 쪽을 맡는다는 것을 구별한다
  • 요구사항 관리 도구의 기능(저장·ID·버전, 추적성, 변경 이력·영향 분석, 상태·보고서)을 분석자동화 도구(CASE)의 기능과 구별한다
  • 요구사항 추적표(RTM)와 양방향 추적(정방향 = 누락 발견, 역방향 = 근거 없는 기능 발견)을 구별한다
  • 변경 관리 절차(요청 → 영향 분석 → CCB 승인 → 반영 → 기준선 갱신)의 순서와 위반 선지를 구별한다
  • 기준선(Baseline)의 의미를 구별한다

1. 큰 그림 — 요구사항 공학 = 개발 + 관리

요구사항 공학은 두 덩어리예요. 요구를 만들어 가는 요구사항 개발(도출 → 분석 → 명세 → 확인)과, 그렇게 만든 요구가 바뀌고 이어지는 것을 다루는 요구사항 관리. 개발 4단계는 한 번 지나가면 끝나는 순서지만, 관리는 도출 이후 운영 중 변경까지 처음부터 끝까지 깔려 있어요.

도분명확 + 관리는 처음부터 끝까지 — 도출·분석·명세·확인은 순서, 관리는 바닥에 깔린 막대.

※ 개발 단계 수·이름은 자료마다 조금 달라요(분석·협상을 묶거나 시스템 모델링을 넣기도 함). 수험 자료는 대부분 “도출·분석·명세·확인” 4단계이고, 마지막을 “확인 및 검증”이라고 쓰는 곳도 있어요.

2. 요구사항 관리 도구가 하는 일

요구사항을 한 건 한 건 ID가 붙은 레코드로 DB에 넣고, 그 레코드에 설계·코드·테스트를 링크로 걸고, 바뀔 때마다 이력을 남기는 도구예요. 스프레드시트 목록과의 차이는 딱 두 가지, 연결과 이력이 남는다는 점이에요.

저장·식별·버전요구마다 ID 부여, 한곳에 저장, 버전관리
추적성 링크요구 ↔ 상위·하위 요구 ↔ 설계 ↔ 코드 ↔ 테스트
변경 이력·영향 분석누가 언제 왜 바꿨나, 바꾸면 어디가 영향받나
상태 관리제안 → 승인 → 구현 → 검증
기준선 생성합의된 시점의 요구 묶음을 스냅샷으로 고정
보고서·명세서 출력RTM·명세서 문서 내보내기
기출 포인트 — 요구사항 관리 도구의 필요성 3종
① 요구사항 변경 추적 ② 변경에 따른 영향 평가 ③ 변경의 비용·편익 분석
→ 셋 다 “변경”이 주어예요.
“기존 시스템과 신규 시스템의 성능 비교”는 요구사항 관리 도구의 필요성이 아니에요. 성능은 설계·테스트(성능 테스트) 쪽 이야기예요. 필요성 문제에서 “변경”이 안 들어간 선지가 정답(아닌 것) 후보예요.

3. 분석자동화 도구(CASE) vs 요구사항 관리 도구

둘 다 출제기준의 같은 세세항목에 묶여 나와서 섞기 쉬워요. CASE는 모델을, 관리 도구는 요구 항목과 그 변경을 다뤄요.

구분분석자동화 도구 (CASE)요구사항 관리 도구
목적분석 모델 작성 + 모델 간 일관성·모순 검사요구사항의 변경 통제와 추적
다루는 것DFD·ERD·자료 사전 등 모델요구 항목(ID)·추적 링크·버전·상태
대표 기능다이어그램 작성, 오류 검증, 문서·코드 생성추적표(RTM), 영향 분석, 기준선, 변경 이력
주로 쓰는 시점분석·설계(상위 CASE 기준)생명주기 전체(운영 중 변경 포함)
시험 키워드상위/하위/통합, 저장소, SADT·SREM·PSL/PSA추적성, RTM, 영향 분석, 기준선, CCB
CASE = 그림 검사기, 관리 도구 = 변경 장부. 선지에 “일관성·모순 검사”가 보이면 CASE, “추적·영향·기준선”이 보이면 관리 도구.

4. 요구사항 추적표(RTM)와 양방향 추적

RTM(Requirements Traceability Matrix)은 요구사항 하나하나가 어떤 설계·모듈·테스트로 이어지는지 한 줄로 이은 표예요. 지금 식으로 말하면 “이슈 ↔ 설계 문서 ↔ PR ↔ 테스트 케이스” 링크를 한눈에 펼친 표죠. 아래는 예시예요. 빈 칸과 맨 아랫줄을 보세요.

요구 ID요구 내용설계모듈테스트
REQ-01회원 로그인SD-03AuthServiceTC-11
REQ-02비밀번호 재설정SD-04(없음)(없음)
(없음)——ExcelExportTC-30
  • REQ-02: 요구에서 오른쪽(구현·테스트)으로 따라가다 끊김 → 정방향 추적으로 찾은 누락(구현·테스트 빠짐)
  • ExcelExport: 모듈에서 왼쪽(요구)으로 거슬러 올라가니 근거 요구가 없음 → 역방향 추적으로 찾은 근거 없는 기능(“고아” 기능, 불필요·범위 밖 구현 의심)

※ 교과서식 RTM은 행에 한 문서의 ID, 열에 다른 문서의 ID를 놓고 교차 칸에 체크하는 매트릭스로 그리기도 해요. 그때는 체크가 하나도 없는 행·열 = 누락 의심이에요. 모양만 다를 뿐 읽는 법은 같아요.

정누 · 역고 — 정방향은 누락, 역방향은 고아(근거 없는 기능). 추적성의 최종 목적은 변경 영향 분석.

5. 변경 관리 절차와 기준선

기준선(Baseline)은 특정 시점에 공식 검토·합의(승인)된 요구사항의 스냅샷이에요. 이후 변경을 판단하는 기준점이 되고, 기준선이 잡힌 뒤의 변경은 반드시 정식 변경 통제 절차를 거쳐요. git으로 치면 릴리스 태그를 찍은 뒤에는 main에 바로 push하지 않고 리뷰·승인을 거쳐 머지하는 것과 같아요.

① 변경 요청무엇을 왜
→
② 영향 분석일정·비용·연관 산출물(RTM)
→
③ CCB 승인승인 / 반려
→
④ 반영·통보산출물 수정, 관계자 공지
→
⑤ 기준선 갱신새 버전 + 이력 기록
기준선 이전요구를 도출·분석하며 자유롭게 다듬는 단계
아직 공식 합의 전
기준선 이후공식 검토·승인 완료 = 변경의 기준점
바꾸려면 요청 → 분석 → 승인 필수

CCB(Change Control Board, 변경통제위원회)는 개발·테스트·제품·관리 책임자 등으로 꾸려져 변경 요청을 받아들일지 결정하는 조직이에요. 판단 재료는 현재 개발 단계·예산·일정·품질에 미치는 영향이고, 그래서 영향 분석이 승인보다 먼저 와요.

  • 순서 바꾸기 선지가 단골이에요: “반영 후 사후 승인”, “승인 → 반영 → 영향 분석”(분석 없이 승인), “변경 요청 없이 반영”.
  • “기준선은 한 번 정하면 절대 바뀌지 않는다” ×. 승인된 변경이 반영되면 새 기준선으로 갱신돼요. 바꿀 수 없는 게 아니라 절차 없이 바꿀 수 없는 거예요.

6. 도구 선택 시 고려사항 (참고)

도입 비용, 기존 개발 도구(이슈 트래커·형상관리·테스트 도구)와의 연동, 사용 편의성, 다중 사용자·권한 지원 정도를 봐요. 제품 예로는 DOORS, Jama 같은 전용 도구나 Jira 기반 구성이 있지만, 제품명이 시험에 나온다고 단정할 근거는 없어요 — 기능 위주로 기억하세요.

7. 시험 포인트 정리

  • 요구사항 공학 = 개발(도출 → 분석 → 명세 → 확인, 도분명확) + 관리(변경 통제·추적). 관리 도구는 관리 쪽
  • 관리 도구 필요성 = 변경 추적 · 영향 평가 · 비용·편익 분석. 성능 비교 ×
  • “추적성” → RTM·영향 분석. 정방향 = 누락 발견, 역방향 = 근거 없는 기능 발견, 양방향 = 둘 다
  • “기준선” → 공식 승인된 스냅샷 = 변경 통제의 기준점
  • 변경 순서: 요청 → 영향 분석 → (CCB) 승인 → 반영 → 기준선 갱신. 승인 전 반영·분석 없는 승인 ×
  • CASE(모델·일관성 검사) vs 관리 도구(요구 항목·변경·추적) 구별

8. 오답 복습 (D+1 두 건)

D005-2 — 부정형 “아닌 것”

어제 “분석자동화 도구의 기대효과가 아닌 것”에서 모델 간 일관성 검증을 골랐는데, 그건 상위 CASE의 대표 효과라 맞는 말이었어요. 정답은 “요구사항 정의 활동 자체가 불필요해짐” — 도구는 정의된 요구를 기록·검증하도록 도울 뿐 정의를 대신하지 않아요.

“아닌 것 / 옳지 않은 것” 문제 읽는 법
① 선지를 보기 전에 질문 끝 단어(아닌·옳지 않은·틀린)에 동그라미 ② 선지마다 O/X를 먼저 붙이기 ③ X가 하나만 남을 때 고르기. 익숙한 키워드가 보인다고 바로 고르면 “맞는 말”을 고르게 돼요.

D004-1 — 럼바우 OMT 기능 모델 = DFD

두 번 연속으로 짝이 엇갈렸어요(10/06 객체 다이어그램, 10/07 동적 모델—DFD). 이번엔 방향을 바꿔서 “그림 → 모델”로도 떠올려 보세요.

OMT 모델주로 쓰는 그림지난 오답
① 객체 모델객체 다이어그램10/06: 기능 모델에 객체 다이어그램 ✕
② 동적 모델상태 다이어그램10/07: 동적 모델에 DFD ✕
③ 기능 모델DFD (자료 흐름도)— 여기가 정답 자리
움직이면 상태, 흐르면 DFD — 동적(움직임) = 상태가 바뀌는 것 = 상태 다이어그램. 기능 = 데이터가 입력 → 처리 → 출력으로 흐르는 것 = 자료 흐름도(DFD). 반대로 “DFD를 쓰는 모델?” → 흐름 → 기능.

확인 문제

  1. 요구사항 추적표로 역방향 추적을 했을 때 가장 잘 드러나는 문제는?
  2. 기준선이 설정된 요구사항의 변경 처리 순서로 가장 적절한 것은?
  3. (오답 재확인) 분석자동화 도구(CASE)에 대한 설명으로 옳지 않은 것은?
  4. (오답 재확인) 럼바우 OMT에서 자료 흐름도(DFD)로 표현하는 모델은?

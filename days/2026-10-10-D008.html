D008 · 스토리보드와 UI 설계 도구 — 와이어프레임·목업·프로토타입 구별

2026-10-10 · A2 소프트웨어 개발 > 화면 설계

현업에서는 Figma 파일 하나에 뼈대·시안·클릭 시뮬레이션·화면 설명이 다 들어 있는 경우가 많죠. 시험은 이걸 와이어프레임 · 목업 · 스토리보드 · 프로토타입 · 유스케이스 다섯 이름으로 쪼개서 “이 설명은 어느 도구인가”를 물어요. 구별 축은 딱 두 개 — 얼마나 실물 같은가(충실도), 눌러서 움직이는가(동작) — 이고, 스토리보드는 그 축 밖의 문서라는 것만 잡으면 돼요.

  • 스토리보드의 정의(정책·프로세스·콘텐츠 구성·와이어프레임·기능 정의·DB 연동까지 담아 디자이너·개발자가 최종 참고하는 설계 문서)와 생김새(왼쪽 화면 · 오른쪽 번호별 Description · 위쪽 문서 정보)를 설명한다
  • UI 설계 도구 5종을 충실도·동작 여부·용도로 구별한다 — 핵심 짝: 목업 = 정적, 프로토타입 = 동적
  • 프로토타입의 종류 페이퍼 / 디지털을 구별하고, 프로토타입을 쓰는 이유(사용성 테스트·조기 피드백)를 설명한다
  • 도구 순서·대표 툴은 자료마다 다르다는 것을 알고, 시험에서는 정의 키워드로 고른다

1. 큰 그림 — A2 지도에서 오늘 위치

어제 본 A2 지도예요. 오늘은 위 상자의 스토리보드와 아래 상자의 UI 설계 도구 두 칸이에요. 둘은 출제기준상 다른 세부항목에 있지만, 스토리보드가 UI 설계 도구 목록에도 다시 등장해서 같이 보는 게 효율적이에요.

2. 두 축으로 보는 UI 설계 도구

와이어프레임·목업·프로토타입은 같은 화면을 점점 실물에 가깝게 만든 단계별 모형이에요. 가로축은 충실도(lo-fi → hi-fi), 세로축은 동작 여부예요. 스토리보드는 이 모형들(주로 와이어프레임)에 설명을 붙여 묶은 문서라 축 바깥 테두리로 그렸고, 유스케이스는 화면이 아니라 요구 쪽 도구라 아래에 따로 뒀어요.

3. 같은 로그인 화면, 세 가지 모형

세 모형의 차이를 한 화면으로 보면 이래요. ②와 ③은 그림으로는 똑같아요. 차이는 ③만 버튼을 누르면 다음 화면으로 넘어간다는 것 — 시험이 노리는 지점이 정확히 여기예요.

4. 5도구 비교표

도구정의 · 주 용도충실도 · 동작
와이어프레임영역·배치만 선과 박스로 잡은 뼈대 · 기획 초기 레이아웃 협의낮음 · ✕
목업색·이미지·문구까지 넣어 실제 화면과 비슷한 모형(구현 안 됨) · 디자인 검토높음 · ✕ 정적
스토리보드화면 + 번호별 Description으로 정책·프로세스·기능·DB 연동까지 담은 문서 · 디자이너·개발자 최종 참고문서 (축 밖)
프로토타입와이어프레임·스토리보드에 인터랙션을 입혀 동작해 보는 모형 · 사용성 테스트높음 · ○ 동적
유스케이스사용자가 목표를 이루려고 시스템과 주고받는 기능 요구 · 다이어그램 → 명세서— (화면 아님)
뼈대 · 시안 · 문서 · 동작 · 시나리오 — 와이어프레임은 뼈대, 목업은 시안, 스토리보드는 문서, 프로토타입은 동작, 유스케이스는 사용자 시나리오. 그리고 “목정프동”: 목업 정적, 프로토타입 동적.

※ 도구별 시험 키워드는 9절 “시험 포인트”에 모아 뒀어요.

유스케이스는 A1에서 본 그 UML 유스케이스 다이어그램(액터·유스케이스·include/extend)과 같은 개념이에요. 유스케이스 다이어그램을 그린 뒤 각 유스케이스의 흐름을 유스케이스 명세서로 풀어 써요. UI 설계 도구 목록에 들어 있어도 “화면을 그리는 도구”는 아니라는 점이 함정 포인트예요.

도구자주 소개되는 툴 (예시)
와이어프레임손그림, 파워포인트, 키노트, 스케치, 발사믹
목업파워 목업, 발사믹 목업
스토리보드파워포인트, 키노트, 스케치, Axure
프로토타입HTML/CSS, Axure, Flinto, 프로토나우, 카카오 오븐

※ 툴 분류는 자료마다 섞여 있어요(발사믹은 와이어프레임 도구로도, 목업 도구로도 소개되고 Axure는 스토리보드·프로토타입 양쪽에 나와요). 툴 이름으로 정답을 고르기보다 정의 키워드로 고르세요.

5. 스토리보드 해부

스토리보드는 “그림”이 아니라 설계서예요. 실제 모양은 거의 정해져 있어요 — 위쪽에 문서 정보, 왼쪽에 화면, 오른쪽에 번호로 짝지은 설명(Description).

스토리보드 한 벌에 담기는 정보는 이 여섯 가지예요. “정보가 가장 많이 실린 문서”라고 기억하면 선지에서 바로 보여요.

정책서비스 운영 규칙 (예: 5회 실패 시 잠금)
프로세스업무·화면 흐름, 페이지 간 이동
콘텐츠 구성화면에 들어갈 내용·문구
와이어프레임화면 레이아웃(UI/UX)
기능 정의버튼·입력 처리 로직
DB 연동어떤 데이터를 조회·저장하나

현업 비유로는 화면 설계서 + 기능 명세 + 예외 정책을 한 문서로 합친 것이에요. SI 프로젝트에서 “화면정의서”라 부르며 개발·테스트·검수 기준으로 쓰는 문서가 바로 이 자리예요. 작성은 대체로 메뉴 구성(IA) → 화면별 레이아웃(와이어프레임) → 번호별 Description 작성 → 이해관계자 검토 순으로 진행돼요.

스토리보드 = 모든 정보 + 최종 참고. 선지에 “디자이너와 개발자가 최종적으로 참고”, “정책·기능 정의·DB 연동”, “Description”이 보이면 스토리보드.

※ 스토리보드에 적는 항목은 자료마다 표현이 달라요(“제목·작성자 / UI 화면 / 디스크립션”, 또는 “주제·화면 제목·화면 구성·화면 설명·연결 화면”). 버전 표기는 실무 관행이에요. 구조(화면 + 번호 설명 + 문서 정보)만 잡아 두면 충분해요.

6. 프로토타입 — 페이퍼 vs 디지털

프로토타입은 와이어프레임이나 스토리보드에 인터랙션을 입혀 실제 서비스처럼 눌러 보게 만든 시제품이에요. 개발 전에 사용자에게 써 보게 하고(사용성 테스트) 피드백을 일찍 반영하려고 만들어요. 만드는 방식에 따라 두 가지로 나눠요.

페이퍼 프로토타입종이·포스트잇에 손으로 그려 사람이 직접 화면을 바꿔 가며 보여 주는 아날로그 방식
디지털 프로토타입파워포인트·Axure·HTML 등 프로그램으로 만들어 실제 기기에서 눌러 보는 방식
구분장점단점
페이퍼빠르고 비용이 거의 없음, 회의 중 바로 고쳐 그림공유·보관·재사용이 어려움, 실제 동작 느낌이 약함
디지털실제와 비슷한 체험, 원격 공유·재사용·수정 이력 관리도구 숙련과 제작 시간 필요

※ 위 장단점은 일반적인 정리예요(이번에 수험 자료 원문과 대조하지 못했어요). 시험은 대부분 “페이퍼 = 손으로 직접, 디지털 = 프로그램 사용” 구분까지만 물어요.

프로토타입을 쓰는 이유: 사용성 테스트, 사용자 피드백을 개발 전에 반영, 요구사항 오해 줄이기, 작업자(기획·디자인·개발) 간 이해 맞추기.
프로토타입은 완성품이 아니에요. 눌러 보니 다 되는 것 같아서 “거의 다 만들었네”로 착각하면 일정·기대가 꼬여요. 시험에서도 “프로토타입 = 최종 제품”식 선지는 ✕.

7. 순서·위치는 자료마다 달라요

“어떤 순서로 만드나”, “무엇이 가장 정밀한가”는 수험 자료끼리도 다르게 적혀 있어요.

자료 계열설명 방식
A와이어프레임 → 목업 → 프로토타입 → 스토리보드(최종 명세)
B와이어프레임 → 스토리보드(설명 추가) → 프로토타입(스토리보드에 인터랙션)
C와이어프레임 → 목업 → 프로토타입은 완성도 축, 스토리보드는 축 밖의 문서

그래서 순서 자체보다 모든 자료가 일치하는 네 가지를 잡으세요.

  1. 와이어프레임이 가장 초기 단계다
  2. 충실도는 와이어프레임 < 목업 < 프로토타입(동작까지 포함하면)
  3. 목업 = 정적, 프로토타입 = 동적
  4. 스토리보드 = 디자이너·개발자가 최종 참고하는, 정보가 가장 많은 문서

8. 단골 함정

  • “목업은 클릭해서 화면 전환을 확인할 수 있다” → ✕ (그건 프로토타입)
  • “와이어프레임 단계에서 색상·이미지까지 확정한다” → ✕ (선과 박스의 뼈대)
  • “스토리보드는 화면 그림만 모은 것 / 디자인 스타일 가이드다” → ✕ (설명·정책·기능·DB까지 담은 설계서)
  • 와이어프레임과 스토리보드 정의 바꿔치기 — “디자이너·개발자가 최종 참고하는 문서 = 와이어프레임” → ✕
  • “유스케이스는 화면 레이아웃을 그리는 도구다” → ✕ (사용자 목표·기능 요구 표현)

9. 시험 포인트 정리

  • “정책 · 프로세스 · 기능 정의 · DB 연동 · 최종 참고 · Description” → 스토리보드
  • “실제 화면과 유사하지만 정적, 실제 구현은 안 됨” → 목업
  • “인터랙션 · 동적 · 시뮬레이션 · 사용성 테스트” → 프로토타입
  • “뼈대 · 레이아웃 · 개략 · 기획 초기” → 와이어프레임
  • “사용자 목표 · 기능 요구 · 다이어그램 → 명세서” → 유스케이스
  • 프로토타입 종류 = 페이퍼(손으로) · 디지털(프로그램으로)
  • 출제기준 위치: 스토리보드 = UI 요구사항 확인, UI 설계 도구 = UI 설계

10. 오답 복습 — 워크숍 (D+7)

10/03 D001 2번에서 틀렸던 요구사항 도출 기법을 오늘 다시 확인해요(확인 문제 3번).

부딪히는 요구를 한자리에서 합의 → 워크숍. 설문은 다수에게 같은 질문, 관찰은 실제 업무 행동 보기, 문서 분석은 기존 자료에서 요구 찾기 — 셋 다 “합의”를 만드는 수단은 아니에요.

D006·D007 답장이 아직이면 내일 D009 주간 복습에서 다시 나와요. 그래서 오늘 새 범위 문제는 2개로 줄였어요.

확인 문제

  1. 디자인 검토를 위해 색·이미지·실제 문구까지 넣어 완성 화면과 거의 똑같이 만들었지만, 버튼을 눌러도 아무 반응이 없는 정적인 화면 모형은?
  2. 화면 그림 옆에 번호별 설명(Description)으로 처리 로직·분기·예외 처리를 적고, 정책·기능 정의·DB 연동 정보까지 담아 디자이너와 개발자가 최종적으로 참고하는 설계 산출물은?
  3. (오답 복습) 새 결제 화면을 두고 보안팀은 추가 인증 단계를, 마케팅팀은 결제 단계 축소를 요구해 의견이 맞선다. 진행자를 두고 두 팀 대표가 한자리에 모여 쟁점을 정리하고 합의안을 만들려 할 때 알맞은 요구사항 도출 기법은?

고른 뒤 답안 복사 → 디스코드 공부 채널에 붙여넣기 하면 돼요.

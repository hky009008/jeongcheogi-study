1. A2 지도 — 마지막 칸

2. 감성공학이란

감성공학(Kansei Engineering) = 사람이 제품에서 느끼는 감성(고급스럽다·답답하다·쾌적하다 …)을 정성·정량적으로 측정하고 과학적으로 분석해서 제품·UI 설계에 반영하는 인간 중심 설계 기술.

현업 감각으로는 “만족도 설문·A/B 테스트·사용성 테스트로 느낌을 숫자로 바꿔 디자인 결정에 쓰는 것”이에요. 목적은 사용자가 편리·안전·쾌적하게 쓰도록 하는 것, UI에서는 HCI 설계에 감성을 반영하는 것이에요. 이름은 1988년 국제 인간공학 학회에서 붙었다고 소개돼요.

색·톤금융 앱의 짙은 파랑 = 신뢰감
햅틱결제 완료 짧은 진동 = 확실함
애니메이션 속도너무 느리면 답답, 빠르면 경쾌
폰트·여백넓은 여백·세리프 = 고급스러움

3. 감성공학 1·2·3류 — 말 · 마음 · 몸

시험에 나오는 건 거의 이 분류예요. 감성을 무엇으로 붙잡느냐가 다릅니다. 1류는 사람이 말로 표현한 감성, 2류는 그 사람 자체(개인·문화), 3류는 기계로 잰 몸의 반응이에요. 1류 → 3류로 갈수록 주관에서 객관으로 옮겨 가요.

분류감성을 잡는 방법강조 특성시험 키워드
1류감성 어휘(형용사)로 제품 이미지를 조사해 디자인 요소와 연결 (의미 미분법 등)감성 이미지형용사 · 감성 어휘 · 이미지
2류개인의 생활방식·특성으로 이미지를 구체화, 문화적 감성 일부 반영심리적개인 · 문화 · 심리
3류감성 어휘 대신 공학적으로 감각을 계측 → 수학적 모델, 물리적 특성과 객관 지표의 연관 분석생리적측정 · 정량 · 수학 모델 · 생리

※ 이 1·2·3류 정리는 여러 수험 자료가 일치하는 기준이에요(분류를 제안한 연구자로 나가마치 미츠오가 소개되기도 해요). 일부 요약은 4류까지 두거나 1류를 “인터뷰 같은 질적 자료”로 설명하는 등 다르게 적어요. 시험에서는 형용사 → 1류, 심리·문화 → 2류, 측정·생리 → 3류로 고르면 돼요.

감성공학을 이루는 요소 기술은 세 단계로 소개돼요.

기반 기술인간 특성 파악 (생체·감각 계측, 인간공학)
→
구현 기술센서·디스플레이·퍼지/신경망으로 인터페이스 구현
→
응용 기술사용성 평가·VR로 적합성 판단, 새 감성 창출
1류 말, 2류 마음, 3류 몸 — 형용사는 말, 심리·문화는 마음, 생리·센서 측정은 몸.
감성공학 레벨표: 1류 = 형용사 수집러(“고급지다”, “귀엽다” 어휘로 이미지 파악) / 2류 = 같은 디자인도 연령·성별·문화마다 느낌이 다르다는 걸 챙기는 단계 / 3류 = 센서·측정·수학 모델까지 가는 공대 감성. 숫자로 재기 시작하면 3류.
“2류 = 생리적 특성 강조”, “3류 = 심리적 특성 강조”처럼 심리↔생리를 바꿔 놓은 선지가 단골이에요. 또 “감성 어휘 대신 공학적 측정”은 이름에 어휘가 나와도 3류예요.

A3 애플리케이션 설계는 세부항목 2개, 세세항목 8개예요. 오늘은 첫 칸 설계 모델링이고, 나머지는 이번 주에 하루씩 채워요.

6. 설계 모델링 — “무엇을”에서 “어떻게”로

A1에서 한 분석 모델링(DFD·OMT 등)은 무엇을 만들지 이해하는 그림이었어요. 설계 모델링은 그 요구를 어떻게 구현할지 정하는 청사진 — 소프트웨어의 내부 기능·구조·동적 행위를 모델로 표현해 분석·검증하는 작업이에요.

분석 모델링 (A1)무엇을(What) · 요구를 이해하고 정리 · DFD, OMT, 유스케이스
설계 모델링 (A3)어떻게(How) · 구현 방법을 구체화 · 아키텍처, 모듈, 인터페이스

설계 모델링에서 지킬 원칙으로 네 가지가 소개돼요.

변경 용이바뀌어도 고치기 쉽게 구조화
필요한 자료만주어진 기능에 필요한 자료만 사용
독립 모듈 분할독립적·기능적인 모듈 단위로 나눔
계층 구조계층적 구조를 가짐

무엇을 모델링하느냐에 따라 두 가지로 나눠요. A1에서 본 UML 구조(정적) / 행위(동적) 다이어그램 구분과 같은 생각이에요.

구조 모델링구성 요소와 그 관계 = 뼈대 · 프로시저, 데이터 구조, 모듈, 파일 구조 · (UML 클래스·컴포넌트처럼 정적)
행위 모델링언제·어떤 순서로 동작 · 입출력 데이터, 데이터 흐름·변환·저장 · (UML 시퀀스·상태처럼 동적)

7. 상위 설계 vs 하위 설계

상위 설계 = 건물 골조(아키텍처·DB 큰 구조, 한 번 정하면 바꾸기 비쌈) / 하위 설계 = 인테리어(모듈·자료구조·알고리즘 상세). 골조를 금요일에 바꾸면 쉽지 않다.

설계는 크게 두 층이에요. 건물로 치면 배치도·평면도(상위)와 방별 배선·배관 상세도(하위)예요.

자료 계열상위 설계하위 설계
A아키텍처 · 데이터 · 인터페이스 · UI모듈 · 자료구조 · 알고리즘
B아키텍처 · 인터페이스 · 자료구조 · 프로시저 · 협약에 의한 설계모듈 설계만
모든 자료가 일치하는 것: 아키텍처 설계 = 상위(예비) 설계, 모듈 설계 = 하위(상세) 설계, 인터페이스 설계 = 상위. “자료구조 설계는 상위인가 하위인가”는 자료가 엇갈리니 단정하는 선지는 조심하세요.

협약에 의한 설계(Design by Contract)는 현업의 assert·계약 프로그래밍과 같은 생각이에요. 컴포넌트를 쓸 때 지켜야 할 조건을 세 가지로 명시해요.

선행 조건호출 전에 참이어야 함 (입력 검증)
결과 조건실행 후 보장되어야 함 (반환값 조건)
불변 조건실행 내내 항상 참 (객체 상태 규칙)

※ 설계 원리(분할과 정복·추상화·단계적 분해·모듈화·정보은닉)와 상향식/하향식 설계는 내일 D011 아키텍처에서 본문으로 다뤄요.

8. 공통 모듈과 명세 원칙 — 정명완일추

공통 모듈은 여러 기능·프로그램이 함께 쓰는, 독립적으로 컴파일·재사용할 수 있는 모듈이에요. 날짜 변환, 코드 값 변환, 금액 포맷 유틸 같은 것들이죠. 여러 곳에서 쓰는 만큼 명세를 엄격하게 써야 하고, 그 기준이 다섯 원칙이에요.

원칙뜻어기면 이런 모습
정확성실제 구현 시 필요한 기능인지 알 수 있도록 정확히 작성필요 없는 기능까지 공통 모듈에 넣어 둠
명확성해당 기능을 이해할 때 한 가지로 해석되도록 작성“적절히 반올림한다” — 사람마다 다르게 읽음
완전성시스템 구현에 필요한 것을 빠짐없이 기술빈 값·음수 입력 처리 규칙이 없음
일관성공통 기능들 사이에 상호 충돌이 없도록 작성날짜 모듈은 KST, 시간 모듈은 UTC 기준으로 서로 어긋남
추적성공통 기능의 요구사항 출처와 관련 시스템 등의 관계를 식별할 수 있도록 작성이 기능이 어느 요구에서 나왔고 누가 쓰는지 모름
정명완일추 — 정확성·명확성·완전성·일관성·추적성. “정명이 완전히 일관되게 추적한다”로 외워도 돼요.
정명완일추 — 정확·명확·완전·일관·추적. 추적성 없는 공통 모듈 = “이 코드 누가 왜 넣음?” 레전드 미스터리 발생. git blame 해도 요구사항까지는 안 나와요.
이름이 A1의 요구사항 명세 품질(D005)·요구사항 추적(D006)과 겹쳐서 헷갈리기 쉬워요. 공통 모듈 원칙 문제에서는 정의 문구로 고르세요 — “공통 기능 간 충돌 없음” = 일관성, “요구사항 출처·관련 시스템 식별” = 추적성, “한 가지로 해석” = 명확성, “모든 것을 기술” = 완전성.

9. 시험 포인트 정리

  • “형용사 · 감성 어휘 · 이미지 조사” → 감성공학 1류
  • “개인 특성 · 생활방식 · 문화 · 심리적” → 2류
  • “공학적 감각 측정 · 수학적 모델 · 객관 지표 · 생리적” → 3류
  • 요구분석의 “무엇을”을 “어떻게”로 바꾸는 청사진 → 설계 모델링
  • 구성 요소·관계 = 구조 모델링, 데이터 흐름·변환·저장 = 행위 모델링
  • 예비 설계 = 상위 설계(아키텍처), 상세 설계 = 하위 설계(모듈)
  • 공통 모듈 명세 원칙 = 정명완일추, “상호 충돌 없음” = 일관성, “요구 출처 식별” = 추적성
